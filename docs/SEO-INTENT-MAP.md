## 1. Принцип

Агрегатор бере запит там, де є вибір. Де вибору немає, запит бере сторінка єдиного партнера.

**Одиниця підрахунку – місто × вузол.** Вузол – це діагноз (Hub) або метод/операція (Case). Кількість партнерів рахується окремо для кожного вузла: у місті може бути 2 партнери по діагнозу і по 1 на кожен метод.

**Партнер** – клініка на піддомені або лікар (лікар = бренд конвеєра, DOCTOR-BRAND-STANDARD §1). Рахується лише партнер з живою сторінкою на цей вузол.

## 2. Розподіл інтентів

| Запит | Стан у місті | Власник |
|---|---|---|
| «діагноз» без міста | – | Hub агрегатора, без гео |
| «метод/операція» без міста | – | Case агрегатора, без гео |
| «діагноз + місто» (напр. «лікування пролапсу Харків») | 0 партнерів | Hub без міста, гео-секція |
| | 1 партнер | сторінка напрямку партнера |
| | 2+ партнерів і 2+ методи | **Hub-місто** агрегатора |
| | 2+ партнерів, усі на одному методі | **Case-місто** цього методу; діагноз у title (§3.1) |
| «метод + місто» (напр. «кольпорафія Харків ціна») | 0 партнерів | Case без міста, гео-секція (fallback) |
| | 1 партнер | сторінка методу партнера (піддомен клініки або сайт лікаря, §4) |
| | 2+ партнерів | **Case-місто** агрегатора з оферами всіх партнерів |
| «чекап + місто» | – | City Catalog агрегатора |
| «чекап [стать] [вік] + місто» | – | вікова сторінка агрегатора, незалежно від кількості партнерів (§6) |
| бренд клініки / ім'я лікаря / «бренд або ім'я + метод» | – | піддомен клініки, сайт лікаря; власний домен – виняток (DOCTOR-BRAND-STANDARD §2) |

## 3. Міські сторінки агрегатора

**Типи:**
- **Hub-місто** – діагноз у місті: хто в місті лікує, які методи де доступні, офери партнерів, згруповані за методом.
- **Case-місто** – метод у місті: офери всіх партнерів з ціною і датою ціни, нейтральне зіставлення без оцінок.

### 3.1 Умови появи

- **Case-місто** – коли на метод у місті є другий партнер з живою сторінкою.
- **Hub-місто** – коли в місті 2+ партнерів по діагнозу **і** доступно 2+ методи (у різних партнерів або в одного).
- 2+ партнерів, але всі на одному методі → Hub-місто не створюється, бо воно дублювало б Case-місто (ті самі офери, той самий метод). «Діагноз + місто» бере Case-місто, діагноз додається в його title (напр. «Кольпорафія при пролапсі в Харкові»).
- Раніше умов не створюється: сторінка з одним офером = агрегатор без вибору, тонка сторінка.

### 3.2 Hub і Hub-місто: що відрізняється

| | Hub без міста | Hub-місто |
|---|---|---|
| Інтент | інформаційний: діагноз, метод не обрано | локально-навігаційний: діагноз + місто |
| Title/H1 | діагноз + симптоми/лікування, без міста | «Лікування [діагнозу] в [місті]: N клінік, методи і ціни» |
| Ядро | що це, ступені, коли без операції, усі методи, як обрати | хто лікує в місті, які методи де доступні, ціни з датою, адреси, лікарі, ПМГ у закладах міста |
| Медичний текст | повний | 2–3 речення, написані окремо, + посилання на Hub |
| Офери | гео-секція по всіх містах | лише партнери міста, згруповані за методом |
| FAQ | медичні («чи можна без операції») | локальні («чи оперують за ПМГ у [місті]», «скільки коштує в [місті]») |
| Розмітка | MedicalWebPage, MedicalCondition | MedicalWebPage + ItemList оферів (MedicalClinic / Physician з адресою, Offer з ціною) |
| Головна дія | консультація для вибору методу | вибір клініки/лікаря → сторінка партнера → запис |

### 3.3 Захист від сторінок-двійників

- Hub-місто і Case-місто не копіюють медичний текст сторінки без міста. Методи на Hub-місті подаються як «доступно в місті / у кого», а не як опис методу.
- Міська сторінка без реальних локальних даних (офери, ціни з датою, адреси, лікарі) не публікується. Набір міських сторінок, що відрізняються лише назвою міста, Google розцінює як doorway pages і знижує всі разом.
- Кожна сторінка self-canonical; міська сторінка ніколи не ставить canonical на сторінку без міста.

### 3.4 Переходи

**1 → 2 партнери:**
1. Партнера, який брав гео, повідомити до публікації другого офера.
2. Агрегатор публікує міську сторінку (за §3.1).
3. Сторінка першого партнера знімає місто з title/H1 у наступному релізі, таргет стає «бренд/ім'я + вузол».

**2 → 1 (партнер вийшов)** [пропозиція, не перевірено]: міська сторінка – 301 на сторінку вузла без міста; партнер, що лишився, може повернути місто в title.

**Без міської сторінки (0–1 партнер):** Hub/Case без міста має гео-секцію (H2 «[Вузол]: де лікують» або «[Операція] в [Місто]») з оферами або рекомендацією найближчого міста.

## 4. Сторінка лікаря і гео

- У місті є клініка-партнер з тим самим вузлом або 2+ партнерів → сторінка лікаря без міста в title/H1.
- Лікар – єдиний партнер у місті на цей вузол → сторінка лікаря може брати «вузол + місто» в title (H1 – на розсуд редактора), за тим самим правилом, що піддомен клініки.
- Поява другого партнера → лікар знімає місто з title за §3.4.
- ПІБ лікаря обов'язковий у title, description і hero (текстом у серверному HTML); у H1 не обов'язковий.

Причина (v4): правило v3 «незалежно від кількості партнерів» виведене з Харкова (пілот 1, де вже є клініка-партнер) і в місті, де лікар єдиний партнер, лишало запит без власника (Київ, Бондарук). Узгоджено з DOCTOR-BRAND-STANDARD §1 «лікар = сутність клініки». Гіпотеза «сайт лікаря не генерує холодний гео-трафік» перевіряється на пілоті 2.

## 5. Гранулярність Case

- Case на окремий метод, якщо за методом є пошуковий попит (GSC / Similarweb).
- Груповий Case (кілька методів однієї групи), якщо окремого попиту немає.
- Рішення – до першого релізу напрямку. Ділити опублікований груповий Case потім – з 301 і втратою ваги.
- Case-місто існує лише для того Case, на який є 2+ партнери в місті.

## 6. Чекапи: вікові сторінки (рішення 30.09)

- «чекап [стать] [вік] + місто» → вікова сторінка агрегатора, незалежно від кількості партнерів.
- Піддомен клініки: сторінка всіх програм, сторінки програм, сторінки лікарів для чекапів. Вікових сторінок на піддомені немає.
- Сторінка програми на піддомені: title/H1 = бренд + назва програми; вік і місто не є таргет-фразою (вік – атрибут у тексті).
- Посилання вікова сторінка → сторінка програми на піддомені, одностороннє.
- Норма самої вікової сторінки: PLATFORM-LINE (чекапи).

## 7. Антиканібалізація і перелінковка

- Агрегатор не таргетить «вузол + місто» в title/H1, поки умови §3.1 не виконані.
- Потік однонаправлений: Hub → Case → партнер; Hub-місто → Case-місто → партнер. Hub → Hub-місто якорем назви міста. Зворотні посилання (Case → Hub, Hub-місто → Hub, Case-місто → Case) – лише хлібні крихти та «інший метод».
- Офер веде на сторінку методу партнера, не на головну. Якщо партнер не виконує метод, його офера в цьому Case немає.
- Партнер (піддомен, сайт лікаря) не лінкує на агрегатор якорем на той самий діагноз або метод.
- Сайт лікаря і піддомен клініки не лінкують одне на одного.
- Між доменами екосистеми – self-canonical; cross-domain canonical не ставимо (приклад: Hub пролапсу на агрегаторі – self-canonical, не на сайт Бондарука, рішення 10.10).
- Власний домен лікаря і піддомен лікаря одночасно на іменний запит – не допускається; при міграції піддомен – 301 постранично, без періоду подвійної індексації.

## 8. URL-схема агрегатора [пропозиція, підтвердити перед міграцією v5]

| Тип | URL |
|---|---|
| Hub | `/ukr/[diagnosis]` |
| Hub-місто | `/ukr/[diagnosis]/[city]` |
| Case | `/ukr/[method]` |
| Case-місто | `/ukr/[method]/[city]` |
| Вікова сторінка чекапу | `/ukr/[sex]-checkup/[age]/[city]` (вже в checkup-main) |

Слаг міста – за SEO-STANDARD §1.

## 9. Приклад: пролапс тазових органів (стан 14.10)

| Вузол | Київ | Харків | Миколаїв |
|---|---|---|---|
| Діагноз «пролапс» | 1 (Бондарук) → сайт лікаря | 1 → партнер | 1 → партнер |
| Метод (кожен) | 1 → сайт лікаря, сторінка методу з містом у title (§4) | 1 → партнер | 1 → партнер |

Агрегатор зараз: Hub «Пролапс» + Case за методами (гранулярність за §5), усі без міста, з гео-секцією. Міських сторінок немає.

Друга клініка в Харкові:
- Клініки роблять різні методи (А – лапароскопічні, Б – вагінальні) → Hub-місто `/ukr/[prolaps]/kharkiv` бере «лікування пролапсу Харків»; на кожен метод по 1 партнеру, тож «сакрокольпопексія Харків» лишається за А, «кольпорафія Харків» – за Б.
- Обидві роблять лише кольпорафію → Hub-місто не створюється; Case-місто `/ukr/[kolporafiia]/kharkiv` з діагнозом у title бере і «кольпорафія Харків», і «лікування пролапсу Харків».
- Обидві роблять 2+ методи, частина спільних → Hub-місто + Case-місто для кожного спільного методу.

## 10. Спостереження з видачі (Харків, ендопротезування, 06.09.2026)

- ШІ-блок Google ставить державну програму (е-черга на безоплатне ендопротезування) на рівень з приватними клініками. Цитує МОЗ, міськраду, Ситенка, da-vinci, onclinic. Персональні сайти лікарів в органіці є, у цитатах ШІ – жодного.
- Висновок: цитований контент = структура (з чого складається ціна, критерії, черга, джерело), не бренд. Аргумент за §4–5 DOCTOR-BRAND-STANDARD як формат.

## 11. Відкрите

- **Власні домени клінік і лікарів:** хто отримує SEO-вагу. Одна політика для клінік (medok) і лікарів. На критичному шляху: міграція Бондарука на власний домен (~листопад 2026). Рекомендація оркестратора: власний домен self-canonical, піддомен 301. Рішення – BOUNDARIES.
- **ПМГ-контент «заклад × процедура»:** сайт лікаря (MVP) чи ПМГ-hub на агрегаторі (беклог). Пропозиція: MVP – блок на сайті лікаря з `source_type=open_data`; після ПМГ-hub – hub canonical.
- **Перехід 2 → 1** (§3.4) – не перевірено на живому випадку.
- **URL-схема** (§8) – підтвердити перед міграцією v5 на check-up.in.ua.
